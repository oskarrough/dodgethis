# Loop

1. **Next.** Take the lowest-numbered brief in `.claude/queue/` whose "after" is met; delete it once it lands. Add new briefs there as they come up. One outcome per thread.
2. **Brief.** At most 10 lines and six acceptance bullets: goal, owned files, done-check, "report in 3 lines". Owned files always include their tests, new files and the doc lines they contradict; a surgical edit elsewhere is fine without asking. Paths come from `bb status`, never typed from memory. Done-checks are proofs by play, not new unit tests (Oskar): a sim change shows a headless match that ends through real play; UI numbers are read from tune. A build fits in about 30 minutes; if it can't, split it. A hero is at least three threads: kit and its tests, views and sounds, bots; run the views and bots threads in parallel once the kit lands. Builders run only the tests near their change plus lint and format on their files; the orchestrator runs the full check at the checkpoint. One screenshot width unless layout is the point. Before a feature's first slice, split its code into one file per system (stands, gallery, ready line), so its slices can go to parallel builders instead of queueing on one; UI and feel slices can run at medium reasoning. Build briefs end with "mashed checkpoint commit on `moba`" and get `.claude/queue/build-rules.md` appended. Reviews use `.claude/queue/review.md` with `<WHAT>` filled in; read the brief back before spawning to check it names its subject. Save the brief to `$BB_THREAD_STORAGE/<slug>.md`. When a review finds a new class of bug, add a line to build-rules.md so the next build avoids it.
3. **Route.** Opus (claude-code) for design. GPT 6.1 (pi) for building and general work. Sonnet for research and smoke tests.
   `bb thread spawn --project proj_dhp5r3qujz --environment <checkout> --parent-self --provider claude-code --model claude-opus-5-5 --reasoning-level high --title "<title>" --prompt-file <brief>`
   For Sonnet: `--model claude-sonnet-5-5 --reasoning-level medium`. For GPT: `--provider pi --model openai-codex/gpt-6.1-sol --reasoning-level high` (without the flag pi runs medium) (if it's missing, run `pi update --all` and upgrade codex). Never leave the provider on its default (pi/GLM).
4. **Parallel.** `<checkout>` is the path in `bb status` for this host: `/home/osk/sites/dodgethis` on the WSL box (12 cores, go wide), `/home/oskar/sites/dodgethis` on hetzner (2 cores: one builder plus one short review). Parallel writers share the checkout: each brief lists the files it owns and says "do not commit"; the orchestrator mashes one checkpoint commit when they land. Queue files are written with Edit or Write at absolute paths and formatted with `bunx oxfmt` straight after. Builds that would share a file run in sequence. Writers may improve what they touch and fix the spec in a line when it's wrong.
5. **Verify.** On completion: `git status --short`, `git diff --stat`, `bun run check`; run `bun run test:slow` once per checkpoint for whole-match and multi-Hz coverage, in a clean worktree of the commit (`git worktree add --detach /tmp/dt-<rev> <rev>`, symlink node_modules): in the shared checkout, live tune.js edits break replays and builders' load breaks the timing budgets. Docs: `wc -l`; the architecture must stay about 10 lines at its core. Gameplay changes: build a frozen copy (`bunx vite build --outDir /tmp/dodgethis-<step>`) and have a Sonnet thread smoke-test that with `agent-browser`, solo and online, while the next build step edits `src/`. agent-browser key presses don't reach the game; use synthetic KeyboardEvents. In a prod build `window.game` appears only after a Backquote toggles diagnostics.
6. **Review.** Review sim, network and state logic, where bugs hide from play. For UI and feel, Oskar playing is the review; don't queue a fix round he hasn't asked for. Spread work over owners: one builder holding every file of a feature serialises it, so split by file before the first slice. An adversarial review by the reverse model: GPT reviews Opus designs, Opus reviews GPT builds. Brief it to find what's wrong, not to summarise, and feed its findings to the author.
7. **Failures.** "Provider rate limit" on claude-code means the Claude session cap: wait for the reset time in the log, then retry, or reroute the work to GPT. "Interrupted" is often the host daemon dropping, not Oskar: read `bb thread log <id> | tail`, and if it says the daemon disconnected, `bb thread retry <id>`. If Oskar stopped it, leave it. A completion notice with no text: read the report from `bb thread log`.
8. **Report.** Update docs/roadmap.md when a big-picture line moves. Then three lines to Oskar: what landed, whether it checks out, what's next. Ask only when a call is his. Then go back to step 1.

After every checkpoint, run a Sonnet new-player smoke (give it a `?play` deep link and Try Mode so objectives are reachable) on a frozen build: reviews judge pieces, only a player finds that the whole is unwinnable or has no exit. Every few steps, spawn an Opus creative thread (name the taste, ban the obvious) and turn the best pitches into queue briefs.

Rules: prototyping, so no git ceremony. Commit only at checkpoints, mashed together ("Add lanes, fix cursor, and tune W") and never with an empty message, and one thread finishes entangled work rather than two splitting it. Short docs; if a doc keeps growing, the design is too big. A thread that produces a file dump was briefed wrong.

The harness is the orchestrator's job too: when the skill, queue, rules or a brief misled a thread or Oskar, fix the file in the same turn.
