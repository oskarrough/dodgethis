# Loop

1. **Next.** Current priority is `roadmap.md` (2026-10-08 feedback): lobby clarity, then small HUD/feel batches, with Mitts gameplay experiments separate. Older `.claude/queue/` briefs are source material for remaining work, never instructions to rebuild shipped features. Add focused briefs as needed; delete them once they land. One outcome per thread. The coordinator owns instructions, briefs, reviews and roadmap updates; builder threads implement game code.
2. **Brief.** Four things, as few lines as they take (Oskar, 2026-10-10): the goal; a checkable finish condition ("done means…"); the evidence to show (a screenshot or clip through `bun run review`, a headless number, before and after); constraints (files or threads to leave alone, commit locally or not, no new unit tests). Example: "Fix the duplicate notification after retry. Reproduce it first. Done means retrying produces exactly one notification and normal delivery still works. Show the failing and passing evidence. Commit locally." Point at docs (feature map, look doc, a page) instead of restating them; never paste rule sections. Save it to `$BB_THREAD_STORAGE/<slug>.md`. When a review finds a new class of bug, add a line to build-rules.md.
3. **Route.** Concept art and generated images: Codex (`--provider codex --model gpt-6.1-sol`, built-in image generator), saved as webp under `docs/pages/<slug>/` with a static `index.html` gallery Oskar opens through the dev server. Opus (claude-code) for design. GPT 6.1 (pi) for building and general work. Sonnet for research and smoke tests.
   `bb thread spawn --project proj_dhp5r3qujz --environment <checkout> --parent-self --provider claude-code --model claude-opus-5-5 --reasoning-level high --title "<title>" --prompt-file <brief>`
   For Sonnet: `--model claude-sonnet-5-5 --reasoning-level medium`. For GPT: `--provider pi --model openai-codex/gpt-6.1-sol --reasoning-level high` (without the flag pi runs medium) (if it's missing, run `pi update --all` and upgrade codex). Never leave the provider on its default (pi/GLM).
4. **Parallel.** `<checkout>` is the path in `bb status` for this host: `/home/osk/sites/dodgethis` on the WSL box (12 cores, go wide), `/home/oskar/sites/dodgethis` on hetzner (2 cores: one builder plus one short review). Parallel writers share the checkout, with no worktrees: each brief lists the files it owns and says "do not commit"; the orchestrator mashes one checkpoint commit when they land. Queue files are written with Edit or Write at absolute paths and formatted with `bunx oxfmt` straight after. Builds that would share a file run in sequence, and so do builds where one deletes or changes an API another calls: split by dependency, not only by file. Writers may improve what they touch and fix the spec in a line when it's wrong.
5. **Verify.** Builders run targeted existing checks, lint and format once (AGENTS.md has the rest); the coordinator inspects the owned diff and runs `bun run check` once at a settled code checkpoint. Run slow whole-match checks when sim/state/timing changed, with other writers and expensive checks idle; never create a verification worktree. Docs-only changes need formatting, not game tests. Browser proofs follow `.claude/skills/verify/SKILL.md`; a full route smoke belongs to a navigation/transition checkpoint, not every builder. Frozen builds and extra smoke agents are reserved for integration uncertainty, not routine UI fixes.
6. **Review.** Review sim, network and state logic, where bugs hide from play. For UI and feel, Oskar playing is the review; don't queue a fix round he hasn't asked for. Spread work over owners: one builder holding every file of a feature serialises it, so split by file before the first slice. An adversarial review by the reverse model: GPT reviews Opus designs, Opus reviews GPT builds. Brief it to find what's wrong, not to summarise, and feed its findings to the author.
7. **Failures.** "Provider rate limit" on claude-code means the Claude session cap: wait for the reset time in the log, then retry, or reroute the work to GPT. "Interrupted" is often the host daemon dropping, not Oskar: read `bb thread log <id> | tail`, and if it says the daemon disconnected, `bb thread retry <id>`. If Oskar stopped it, leave it. A completion notice with no text: read the report from `bb thread log`.
8. **Report.** Oskar owns the look: visual art, style, names and branding (2026-10-10). Everything else (mechanics, feel, bots, balance, UX fixes, the harness) the orchestrator decides and builds, then shows him the result. Questions for Oskar go in roadmap.md's "Waiting on Oskar" list, and leave it when answered. Update `roadmap.md` as feedback goals are implemented and judged; update docs/roadmap.md when a big-picture line moves. Then three lines to Oskar: what changed, whether it checks out, what's next. Ping him at a meaningful visual/feel checkpoint with http://office-linux.heron-mermaid.ts.net:5173 (never a 127.0.0.1 URL); every visual proof or variant goes through `bun run review` and reports link http://office-linux.heron-mermaid.ts.net:5173/docs/pages/, not thread-storage paths and the shortest route, a screenshot for layout or a short clip for motion, plus one concrete judgment. A screenshot alone does not prove feel. Pitches and designs for Oskar's feedback (heroes, maps, settings) are HTML pages under `docs/pages/<slug>/`, served by his dev URL, with numbered items he can reply to, styled only by `<link rel="stylesheet" href="/docs/page.css">` and `<body class="page">` (plain semantic HTML, no CSS of your own); never a markdown file in thread storage. Never invent a URL or deploy by hand. Ask only when a call is his, one question at a time: talk to Oskar in one or two chatty lines and steer the conversation, never a menu of open threads (Oskar, 2026-10-10). Then go back to step 1.

When a checkpoint changes navigation, objectives or match flow, do one relevant new-player smoke. Don't automatically add a browser reviewer or creative thread after each small batch. For UI and feel, make Oskar's judgment easy and adjust the next brief from his feedback.

Rules: prototyping, so no git ceremony. Commit only at explicitly authorized checkpoints, mashed together ("Add lanes, fix cursor, and tune W") and never with an empty message, and one thread finishes entangled work rather than two splitting it. Short docs; if a doc keeps growing, the design is too big. A thread that produces a file dump was briefed wrong.

The harness is the orchestrator's job too: when the skill, queue, rules or a brief misled a thread or Oskar, fix the file in the same turn.

Every HTML artifact lives in `docs/pages/<slug>/` and is an item in `docs/pages/items.json` (`bun run review` adds proofs); when Oskar decides, the orchestrator records it by setting the item's `status` and `decision`.
